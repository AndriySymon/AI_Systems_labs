# Архітектурні підходи: Моноліт проти Мікросервісів

## 1. Коротке резюме
Лекція присвячена порівняльному аналізу монолітної та мікросервісної архітектур, висвітлюючи їхні сильні та слабкі сторони. Автор застерігає від передчасного впровадження мікросервісів без належної інфраструктури та розуміння доменних меж. Головний висновок полягає у дотриманні стратегії «Monolith First», яка дозволяє системі еволюціонувати природним шляхом.

## 2. Детальний конспект за розділами

### Вступ та типові помилки проєктування [00:00]
- **Передчасна декомпозиція**: Поширена помилка нових проєктів — спроба розділити систему на десятки мікросервісів без чіткого розуміння бізнес-логіки.
- **Необхідні умови для мікросервісів**:
    - Чітко визначені **межі домену** (Bounded Contexts).
    - Зріла культура **DevOps** та автоматизація розгортання.

### Монолітна архітектура: переваги та обмеження [04:15]
- **Визначення**: Весь код застосунку збирається та розгортається як **єдиний артефакт**.
- **Переваги**:
    - **Простота розробки**: Легше запускати локально та налагоджувати (debugging).
    - **Цілісність даних**: Підтримка **ACID-транзакцій** на рівні однієї бази даних без потреби в складних розподілених протоколах.
- **Недоліки (проявляються при масштабуванні)**:
    - **Командна робота**: Коли кількість розробників перевищує 15–20 осіб, виникають конфлікти при злитті коду.
    - **Надійність**: Помилка в одному модулі (наприклад, витік пам'яті) може призвести до падіння всього застосунку.
    - **Неефективне масштабування**: Неможливо масштабувати лише один високонавантажений компонент (наприклад, пошук); доводиться копіювати весь моноліт.

### Мікросервісна архітектура та її виклики [11:30]
- **Призначення**: Вирішення проблем масштабування великих команд та високих навантажень.
- **Ключові принципи**:
    - **Database per Service**: Кожен сервіс володіє власними даними; прямий доступ до БД іншого сервісу заборонений.
    - **Комунікація**: Використання синхронних (REST, gRPC) або асинхронних (Kafka, RabbitMQ) протоколів.
- **Ціна впровадження**:
    - **Eventual consistency**: Дані в різних сервісах стають узгодженими не миттєво, а через деякий час.
    - **Складність**: Необхідність у розподіленому трасуванні, складному моніторингу та управлінні мережевими затримками.

### Стратегія Monolith First [18:40]
- **Золоте правило Мартіна Фаулера**: Починати проєкт варто з моноліту.
- **Модульний моноліт**: Підхід, при якому код структурований за функціональними блоками з чіткими інтерфейсами всередині одного артефакту.
- **Еволюційний перехід**: Виділяти окремий мікросервіс слід лише тоді, коли конкретний модуль стає «вузьким місцем» для продуктивності або розробки.

## 3. Словник ключових термінів

| Термін | Визначення простими словами | Таймкод |
| :--- | :--- | :--- |
| **Моноліт** | Архітектура, де всі функції програми працюють як одна ціла програма. | [04:15] |
| **ACID** | Набір правил, що гарантують, що операції з базою даних пройдуть надійно та успішно. | [04:15] |
| **Database per Service** | Правило, за яким кожен мікросервіс має свою власну, ізольовану базу даних. | [11:30] |
| **Eventual consistency** | Стан, коли дані в різних частинах системи стають однаковими не одразу, а через короткий проміжок часу. | [11:30] |
| **Monolith First** | Рекомендація починати розробку з моноліту, щоб краще зрозуміти систему перед її розділенням. | [18:40] |
